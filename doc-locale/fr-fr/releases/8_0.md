Avec la release `17.0` de GitLab, nous avons publié la version `8.0` du chart Helm GitLab.

## Résumé des modifications majeures {#summary-of-major-changes}

- Le workflow d'enregistrement de runner legacy est désormais désactivé par défaut. [Une action manuelle est nécessaire pour migrer vers le nouveau workflow d'enregistrement](#runner-workflow-changes).
- La prise en charge de PostgreSQL 13 a été supprimée. Assurez-vous d'utiliser PostgreSQL 14 ou une version plus récente avant de procéder à la mise à niveau.

Consultez [les notes de mise à niveau de GitLab 17](https://docs.gitlab.com/update/versions/gitlab_17_changes/) pour tous les changements pertinents liés à la mise à niveau.

## Chemin de mise à niveau depuis la version 7.x {#upgrade-path-from-7x}

Pour effectuer la mise à niveau vers la version `8.0` du chart, vous devez d'abord effectuer la mise à niveau vers la dernière release `7.11.x` du chart. Consultez les [détails de la correspondance des versions](../installation/version_mappings.md) pour le dernier correctif.

### Mise à niveau vers la version 8.8.0 {#upgrade-to-880}

Si vous avez désactivé le [job `shared-secrets`](../charts/shared-secrets.md#disable-functionality), vous devrez créer manuellement trois nouveaux secrets. Si vous l'avez activé (comportement par défaut), il n'y a rien à faire, car les nouveaux secrets seront générés automatiquement.

- `active_record_encryption_primary_key`
- `active_record_encryption_deterministic_key`
- `active_record_encryption_key_derivation_salt`

Le format des secrets est disponible dans [la section des secrets GitLab Rails](../installation/secrets.md#gitlab-rails-secret).

Voici les étapes pour renseigner ces 3 secrets :

1. [Sauvegardez les secrets](../backup-restore/backup.md#back-up-the-secrets).
1. Générez 3 chaînes aléatoires différentes de 32 caractères –une pour chacun des nouveaux secrets– avec `LC_ALL=C < /dev/urandom tr -dc 'a-zA-Z0-9' | head -c 32`
1. Ajoutez les secrets à la fin de `gitlab-secrets.yaml`. Assurez-vous que les secrets sont indentés sous la clé `production` :

   ```yaml
   production:
     active_record_encryption_primary_key:
       - "<first 32-chars random string>"
     active_record_encryption_deterministic_key:
       - "<second 32-chars random string>"
     active_record_encryption_key_derivation_salt: "<third 32-chars random string>"
   ```

1. Créez une nouvelle ressource `secret` (remplacez `<name>` par le nom de la release) :

   ```shell
   kubectl create secret generic <name>-rails-secret-v2 --from-file=gitlab-secrets.yaml
   ```

1. Mettez à jour `global.railsSecrets.secret` dans votre fichier `values.yaml` pour pointer vers la nouvelle ressource de secret `<name>-rails-secret-v2`.
1. Mettez à niveau la release du chart GitLab avec cette nouvelle valeur, en vous assurant que les autres anciennes valeurs s'appliquent toujours (par exemple, [n'utilisez pas l'indicateur `--reuse-values`](../installation/upgrade.md)).
1. Confirmez que GitLab fonctionne comme prévu. Si c'est le cas, il devrait être possible de supprimer en toute sécurité l'ancienne ressource de secret `<name>-rails-secret`.

### Mise à niveau vers la version 8.6.0 {#upgrade-to-860}

Le label `app` du job qui effectue les migrations de base de données pour la base de données de métadonnées du registre de conteneurs a été modifié de `registry` à `registry-migrations` pour résoudre les problèmes liés aux sélecteurs du registre de conteneurs `Deployment` et `PodDisruptionBudget`.

Si vous n'avez pas activé la base de données de métadonnées du registre, ou si vous ne l'utilisez pas dans des outils externes tels que des solutions de surveillance ou de journalisation, vous n'avez rien à faire. Si vous utilisez ce label, veuillez le mettre à jour en conséquence.

### Mise à niveau vers les versions 8.6.x, 8.5.1, 8.4.3, 8.3.6 {#upgrade-to-86x-851-843-836}

Cette modification vous concerne uniquement si vous utilisez le [chart GitLab NGINX](../charts/nginx/_index.md) et que vous avez défini vos propres règles de contrôle d'accès basé sur les rôles NGINX.

Si vous utilisez votre propre [chart NGINX externe](../advanced/external-ingress/_index.md), ou si vous utilisez le chart GitLab NGINX sans aucune modification des règles de contrôle d'accès basé sur les rôles NGINX, vous pouvez ignorer cette section.

Dans les versions 8.6.0, 8.5.1, 8.4.3 et 8.3.6 du chart Helm, l'image du contrôleur Ingress NGINX a été mise à jour vers la version v1.11.2, mais la version du chart du contrôleur Ingress NGINX est toujours sur 4.0.6. L'ancienne image du contrôleur `v1.3.1` est désormais dépréciée et prévue pour suppression dans le chart GitLab 9.0.

Lors de la mise à niveau vers les versions de chart mentionnées, la version `v1.11.2` sera définie par défaut. Le chart reviendra automatiquement à `v1.3.1` si vous définissez `nginx-ingress.rbac.create` sur `false` (la même règle s'applique à Geo `nginx-ingress-geo.rbac.create`). Cela est dû au fait que `v1.11.2` nécessite de nouvelles règles de contrôle d'accès basé sur les rôles, que nous avons ajoutées à notre [chart NGINX](../charts/nginx/_index.md).

Si vous gérez vos propres règles de contrôle d'accès basé sur les rôles NGINX et souhaitez utiliser la nouvelle version `v1.11.2` avant qu'elle ne soit imposée dans GitLab 18.0 (chart Helm 9.0) :

1. Appliquez les nouvelles règles de contrôle d'accès basé sur les rôles à votre cluster ([exemple](https://gitlab.com/gitlab-org/charts/gitlab/-/merge_requests/3901/diffs?commit_id=93a3cbdb5ad83db95e12fa6c2145df0800493d8b)) :

   ```yaml
   - apiGroups:
      - discovery.k8s.io
    resources:
      - endpointslices
    verbs:
      - list
      - watch
      - get
   ```

1. Activez l'image du contrôleur `v1.11.2` avec :

   ```yaml
   nginx-ingress:
     rbac:
       create: false
     controller:
       image:
         disableFallback: true
   ```

### Modifications du workflow du runner {#runner-workflow-changes}

Le workflow d'enregistrement de runner legacy est désormais désactivé par défaut. Vous devez [migrer vers le nouveau workflow d'enregistrement](https://docs.gitlab.com/tutorials/automate_runner_creation/) ou [réactiver le workflow legacy](https://docs.gitlab.com/administration/settings/continuous_integration/#control-runner-registration).

Consultez la [documentation du sous-chart runner](../charts/gitlab/gitlab-runner/_index.md#requirements) pour les instructions de migration.

With the `19.0` release of GitLab, we have released version `10.0` of the GitLab Helm chart.

This document highlights the changes with the highest impact. For a comprehensive overview, see:

- [GitLab 19.0 deprecations](https://docs.gitlab.com/update/deprecations/#gitlab-190)
- [A guide to the breaking changes in GitLab 19.0](https://about.gitlab.com/blog/a-guide-to-the-breaking-changes-in-gitlab-19-0/)

## Summary of major changes

- [NGINX Ingress is now disabled by default and replaced by Gateway API with Envoy Gateway.](https://docs.gitlab.com/update/deprecations/#support-for-nginx-ingress)
- [The bundled PostgreSQL, Redis, and MinIO have been removed from the GitLab chart.](https://docs.gitlab.com/update/deprecations/#support-for-bundled-postgresql-redis-and-minio-in-gitlab-helm-chart)
- [Support for PostgreSQL 16 has been removed. Make sure you are running PostgreSQL 17 before upgrading.](https://docs.gitlab.com/update/deprecations/#support-for-postgresql-16)
- [Resource Owner Password Credentials (ROPC) OAuth grant removed.](https://docs.gitlab.com/update/deprecations/#resource-owner-password-credentials-grant-is-deprecated)

For mitigation steps and full details, follow the linked deprecation notices.

## Upgrade to 10.6.0

### Custom certificates images must provide their scripts

The chart now runs these scripts as the container command, instead of the image's default command:

- The `certificates` init container runs `/scripts/bundle-certificates` from `global.certificates.image`.
- The `cfssl-self-sign` container of the self-signed certificates Job runs `/scripts/generate-certificates`
  from `shared-secrets.selfsign.image`.

The Cloud Native GitLab images already provide these scripts.
If you replace either image with your own, make sure the image provides the script at that path.
Otherwise, the Pods that use the image fail to start.
For the requirements of the certificates image, see the
[certificates image contract](../development/certificates_image.md).

### Praefect Service no longer has Prometheus scrape annotations

The Praefect Service no longer has the `gitlab.com/prometheus_*` and `prometheus.io/*` scrape
annotations. With the default values, their port annotations were empty. A Prometheus that read
them scraped every port of the Service, including the Praefect gRPC port. The Praefect Pods keep
their scrape annotations, like Gitaly and the other GitLab components, and the Praefect
ServiceMonitor is unchanged.

If your Prometheus discovers scrape targets only from Service annotations, it no longer scrapes
Praefect. Configure it to discover Pods by their annotations or, if you use the Prometheus
Operator, set `gitlab.praefect.metrics.serviceMonitor.enabled` to `true`. With the bundled
Prometheus, the `kubernetes-pods` job still scrapes Praefect, but the `kubernetes-service-endpoints`
job no longer does. Update any query that selects Praefect metrics with
`job="kubernetes-service-endpoints"`. For the metrics settings, see
[Praefect installation command line options](../charts/gitlab/praefect/_index.md#installation-command-line-options).

### Registry configuration rendered without a shell

The registry `configure` init container now renders `config.yml` with `gomplate` instead of
a shell script, so passwords and other secrets can contain any character. Unless you set
`registry.init.script`:

- The init container image must provide `gomplate` on its `PATH`. This affects you only if
  you set `registry.init.image` or `global.gitlabBase.image` to an image without it.
- `{% %}` in registry chart values is no longer evaluated, and is written to the registry
  configuration unchanged.
- The `registry-server-config` volume holds only `config.yml`. Extra volume mounts or
  containers that read other files from it must mount the Secrets instead.
- A `delete.enabled` value in the `storage` Secret is now always honored. The script
  added `delete.enabled: true` unless the line after `delete:` was an indented
  `enabled:`, so `delete: {enabled: false}`, or a comment or blank line before
  `enabled: false`, left deletes enabled. If you rely on deletes, set
  `delete.enabled: true` or remove the `delete` key.

For details, see
[Configuring the `configure` init container](../charts/registry/_index.md#configuring-the-configure-init-container).

### `configure` init containers removed

The Webservice, Sidekiq, Toolbox, Migrations, Geo Log Cursor, Mailroom, GitLab Exporter,
Gitaly, Praefect, GitLab Shell, and GitLab Pages Pods no longer run a `configure` init
container. Their containers read the Secrets directly. The registry is unchanged.

- The `init.image` setting of these charts is no longer used. These Pods no longer pull the
  `global.gitlabBase.image` image, except Gitaly with `cgroups.enabled`: its `init-cgroups`
  container still takes its image registry and tag from `global.gitlabBase.image`.
- The Pods must run with an `fsGroup`, as the default `securityContext` sets. The secret
  files are owned by `root` and readable by the Pod's `fsGroup`.
- Kubernetes now updates the secret files of a running Pod when you change the Secrets.
  Before, the Pod kept the files it started with.
- The default `gitlab.gitaly.cgroups.mountpoint` reads
  `/etc/gitaly-cgroup/gitaly-pod-cgroup`. A value that reads the previous path,
  `/etc/gitlab-secrets/gitaly-pod-cgroup`, still works.

## Upgrade to 10.4.0

### KAS advertises native gRPC to agents by default

The address in `gitlab_kas.external_url`, shown in the agent installation instructions, now
defaults to `grpcs://kas.example.com` instead of `wss://kas.example.com` when the chart routes
gRPC to KAS: with Gateway API and the chart-managed Envoy Gateway policies (the default), or
with the NGINX Ingress provider, for which the KAS gRPC Ingress is now rendered by default. Other Ingress controllers and installations with a
relative URL root keep `wss://`. Agents already connected over `wss://` are not affected.
To keep advertising WebSocket, set `global.appConfig.gitlab_kas.externalUrl`. To skip the gRPC
Ingress, set `global.kas.ingress.grpc.enabled: false`. For details, see
[agent connection protocol](../charts/gitlab/kas/_index.md#agent-connection-protocol).

## Upgrade to 10.3

### Envoy Gateway upgrade requires new CRDs

The bundled Envoy Gateway chart is upgraded from 1.8.3 to 1.9.1. Helm does not upgrade CRDs, so
apply the Envoy Gateway CRDs for 1.9.1 and the [required version 1.6 Gateway API CRDs](https://gateway.envoyproxy.io/news/releases/v1.9/#-breaking-changes)
before you upgrade GitLab. Otherwise the upgrade fails on the GitLab Shell `TCPRoute`,
and the API server prunes the new `Host` header setting on the Webservice listeners. For the upgrade steps, see
[Upgrade the Envoy Gateway CRDs](../charts/envoygateway/_index.md#upgrade-the-envoy-gateway-crds).
